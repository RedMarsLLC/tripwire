# Requirements status after security review

Status describes the actual implementation. A listed capability can be operational within a narrow scope without establishing broad host coverage. This release is a Phase 1 foundation plus selected tested detection infrastructure.

## Final security-review fixes

- True read-only/query-only evidence connections for viewers, plus first-run in-memory display and later writer discovery.
- Coherent SQLite read transactions while a separate WAL writer commits.
- Private owned database/WAL/SHM files, no-follow target opens, exclusive creation, no chmod of existing insecure files, and private no-follow collector locks.
- Explicit reviewed-fingerprint approval with atomic audit; stale approvals and audit failures leave state unchanged. Reset is rejected.
- Removal inference requires successful declared scope and per-record scope identity across subsequent polls.
- Failed empty snapshots, missing/future/stale heartbeats and GUI read failures cannot leave an Active display.
- Safer canary directory creation and no traversal of symlinked persistence roots.

At review, PID 58059 still identified `/tmp/tripwire-build/debug/tripwire`, launched 2026-10-01 10:12:26 local time. The earlier build-name collision made that binary the GUI. Its open files were `validation/host.sqlite` and SQLite sidecars. It had **no collector-lock descriptor and no child processes**. The old viewer opened a read/write SQLite connection for initial schema setup, so it should not be described as a strictly read-only database connection. Its operating role is a viewer, with no evidence that it started collection. Current deliverables now use an actual read-only connection.
